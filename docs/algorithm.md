# 検知アルゴリズム: 人の動きから「いつもと違う集まり」を見つける

> 実装: `app/detect.py`（純関数）、`app/mesh.py`（地域メッシュ）。答え合わせ: `scripts/synth/detect_demo.py`。テスト: `tests/test_detect.py`
> 入力は「誰が・いつ・どこにいたか」の点列（1 分おき）。出力は「このマス・この時間帯に、いつもと違う集まりがある」という候補。
> 候補の正体（給水・炊き出し・車中泊など）は、その場にいる人に聞いて確定する（CLAUDE.md §2）。アルゴリズムは候補出しまで。

## 1. 考え方

**その人にとって「いつもと違う場所」に 10 分以上とどまった人を、同じ場所・同じ時間帯で数える。**

災害時は「場所ごとに平常時と人数を比べる」方式が崩れる（CLAUDE.md §3・§4）。

- 緊急期は街全体が一斉に「いつもより多い」になる（YJMob100K: 多いマス 1847、少ないマス 2）
- 学校など避難所になる場所は普段から人が多く、災害日は休校で「いつもより少ない」になる

そこで比べる相手を「場所の平常」から「**その人の平常**」に変える。人の移動は規則的で（Song ほか 2010）、いつもの場所から外れた滞在そのものが信号になる。
給水所に来る人は、ふだんそこに来ない人ばかりなので、「いつもと違う滞在」が 1 か所に集中する。通勤や買い物は、その人にとって「いつもの場所」なので数えない。

## 2. 手順

```
点列（1 分おき）
  │ ① 滞在の抽出      100m 以内に 10 分以上
  ▼
滞在（場所・開始・終了）
  │ ② 平常期を分析     自宅 / いつもの場所 / 探索型かどうか（人ごと）
  ▼
いつもと違う滞在     自宅の周り 200m でも、いつもの場所でもない滞在だけ
  │ ③ 集計            500m メッシュ × 30 分（10 分ずらし）、探索型は 0.5 で数える
  ▼
マス × 時間帯の人数
  │ ④ 期待値           その時間帯の街全体の「いつもと違う滞在」の総数 × マスの平常時の割合
  │ ⑤ 判定             ポアソンで上側確率 < 1/1000 かつ 5 人以上 → 候補。続く時間帯はまとめる
  ▼
候補（マス・時間帯・人数・期待値・p 値）→ 公式の拠点から 150m 以内なら「公式」に分ける
```

### ① 滞在の抽出（`stays_from_track`）

1 人 1 日の点列を先頭から見て、基準点から 100m 以内にある点を同じ滞在とみなす。100m を出たら区切り、10 分以上続いていれば 1 滞在として記録する。
基準点は入ってきた点の平均に少しずつ寄せる（GPS 誤差で端に基準が付くのを防ぐ）。

出力: `Stay(lat, lon, start, end)`（start・end はその日の 0:00 からの分）

### ② 平常期の分析（`learn_person`）

平常期（合成データでは 14 日）の滞在から、人ごとに 3 つを決める。

| 何を | どう決める | なぜ |
|---|---|---|
| 自宅 | 平常日の 3:00 の位置の中央値 | 住所を聞かずに決められる。自宅の周り 200m は検知の対象外（プライバシーと、家の集まりは支援拠点でないため） |
| いつもの場所 | 滞在を 150m で場所にまとめ、**2 日以上**行った場所 | 職場・学校・いつもの店。1 回だけの外出は「いつもの場所」にしない |
| 探索型かどうか | 1 回だけ行った場所（自宅の周りを除く）が **6 か所以上** | 新しい場所によく行く人（Pappalardo ほか 2015 のエクスプローラー）は災害時も新しい場所に行きやすく、誤報の元になる。重みを 0.5 にして軽く数える |

### ③ いつもと違う滞在の集計（`detect` 前半）

災害日の滞在のうち、自宅の周り 200m でもいつもの場所でもないものを「いつもと違う滞在」とする。
これを **1/2 地域メッシュ（約 500m 四方、JIS X 0410）× 30 分の時間帯** で数える。時間帯は 10 分ずつずらす（0:00–0:30、0:10–0:40、…）。滞在が時間帯に 10 分以上重なれば数える。
人数は重みの合計（ふつうの人 1、探索型 0.5）。

500m にした理由: 検証に使った実データ（YJMob100K）と国勢調査・経済センサスのメッシュに揃う。30 分にした理由: 給水は 15〜45 分の短い滞在が多く、これより長いと集まりが薄まる。

### ④ 期待値（`baseline_share` + `detect`）

「そのマス・その時間帯に、偶然どれだけの『いつもと違う滞在』が来るか」を期待値にする。

```
期待値(マス, 時間帯) = その時間帯の街全体の「いつもと違う滞在」の総数 × （平常期にそのマスにあった滞在の件数 ÷ 平常期の全滞在の件数）
```

街全体の総数を掛けるのが肝で、**その日の街全体の量に合わせて基準が自動で動く**。災害日に多くの人が新しい場所へ出かけても、総数が増えるぶん期待値も上がり、どのマスでも「多い」とは言わなくなる。
平常期に誰も行かないマスで期待値が 0 になるのを防ぐため、下限を 0.3 にする。

### ⑤ 判定（`poisson_sf`）

人数 k が期待値 λ のポアソン分布からどれだけ外れているかを、上側確率 P(X ≥ k | λ) で測る。

```
P(X ≥ k) = 1 − Σ_{i<k} e^{−λ} λ^i / i!
```

**P < 1/1000 かつ k ≥ 5** なら候補。5 人の下限は「少人数の集まりは表示しない」（CLAUDE.md §2 のプライバシー）のため。
同じマスで候補の時間帯が続けば 1 つにまとめ、人数が最大の時間帯の値を代表にする。最初に候補になった時間帯の終わりが「検知した時刻」。

例: あるマスの平常時の割合が 1%、その時間帯の街全体の「いつもと違う滞在」が 60 件なら λ = 0.6。そこに 8 人なら P(X ≥ 8 | 0.6) ≈ 2.4 × 10⁻⁷ → 候補。
同じ 8 人でも、街全体が 2,000 件（λ = 20）なら P ≈ 0.999 → 候補にならない（街全体が動いている日に、人の多いマスが多少増えても反応しない）。

### 公式の拠点の差し引き

候補の中心が公式の避難所・給水所から 150m 以内なら `official` を付けて分ける。公式の拠点は公式の一覧で分かるので、地図に「非公式」として載せない。
検知自体は公式でも同じように起こる（避難所に人が集まるのは「いつもと違う滞在」なので）。

API の定期処理（`app/detect_job.py` の `_at_official`、`OFFICIAL_M` = 150m）では、その時間帯に開設中の公式の拠点（`official_spots`）から 150m 以内の候補は `candidates` に書かない。公式の緑のピンがもう出ているので、近くの人に聞く必要がないため。答え合わせ（`scripts/synth/detect_demo.py` の `OFFICIAL_M`）では、同じ候補を「公式」として数えずに分ける。

## 3. 判定の基準（`app/detect.py` の定数）

| 定数 | 値 | 意味 | 根拠 |
|---|---|---|---|
| `STAY_RADIUS_M` | 100m | 同じ滞在とみなす半径 | スマホ GPS の屋外誤差（数 m〜数十 m）に余裕を持たせた仮置き |
| `STAY_MIN` | 10 分 | 滞在と数える最短の長さ | CLAUDE.md §3（10 分以上とどまった人数を数える） |
| `PLACE_RADIUS_M` | 150m | いつもの場所の半径 | 仮置き |
| `HOME_RADIUS_M` | 200m | 自宅の周りは対象外 | CLAUDE.md §2 |
| `USUAL_DAYS` | 2 日 | いつもの場所にする日数 | 仮置き（平常 14 日のうち） |
| `EXPLORER_NEW_PLACES` | 6 か所 | 探索型とみなす「1 回だけの場所」の数 | 合成データで探索型 20% に対し 13.5% が該当するように置いた仮値 |
| `WINDOW` / `STEP` | 30 分 / 10 分 | 時間帯の長さとずらし幅 | CLAUDE.md §4（実データは 30 分単位）。10 分ずらしは検知までの時間を縮めるため |
| `MIN_OVERLAP` | 10 分 | 滞在が時間帯に重なる最短 | `STAY_MIN` と同じ |
| `P_THRESHOLD` | 1/1000 | 候補にする上側確率 | 仮置き。確認で誤報を消せるので緩めでよい（CLAUDE.md §3） |
| `MIN_OBSERVED` | 5 人 | 候補にする最少人数 | 少人数の集まりは表示しない（CLAUDE.md §2） |
| `MIN_EXPECTED` | 0.3 | 期待値の下限 | 仮置き |

「仮置き」の値は、合成データの答え合わせ（`scripts/synth/detect_demo.py`）で調整する。調整に使った seed と測定に使う seed は分ける。

## 4. 合成データでの結果

八代市の合成データ（1000 人 = 市民の縮図、1 分刻み、平常 14 日 + 地震当日 + 2 日。`docs/demo-data-design.md`）で答え合わせをした。

| 正解（公式でない集まり） | 件数 | 検知 | 検知までの時間 |
|---|---|---|---|
| 給水車（団地の前・公園、20〜40 人） | 6 | 6 | 30〜60 分 |
| 炊き出し（個人店 25〜30 人、町内会 60〜70 人、物産館 80〜90 人） | 8 | 8 | 10〜30 分 |
| 車中泊（公園・大型店の駐車場、7〜20 人、夜と翌朝） | 15 | 15 | 10〜80 分 |
| 再開した店の行列（38〜44 人） | 2 | 2 | 30〜50 分 |
| **合計** | **31** | **31** | **中央値 30 分** |

誤報 1 件（地震の翌日 15:30、親戚の家への訪問が重なったマス、5 人）。公式給水 3 件は当たっても外れても数えない。

**この数字の扱い（正直に）**
- 上の表は台本を作ったのと同じ seed 1 の「調整用」の値。seed を変えた測定用の 3 本でも同じ結果だった（§4.2）
- 1000 人は市民の縮図。実際のアプリ参加率が 5% なら、30 人の炊き出しはアプリ利用者 1〜2 人にしか見えず検知できない。参加率 5% で見えるのは 200 人規模（アプリ利用者 10 人）から（CLAUDE.md §3・§4）
- 合成データの行動は仮定が多い（`docs/demo-data-design.md` §4）。この結果は実際の災害時の精度を意味しない。実データで確かめた数字は CLAUDE.md §4（YJMob100K: 10 人の集まりを 97〜98% 検知、中央値 90 分）を使うこと

### 4.1 平常期のデータは要るのか（「当日だけ」版との比較）

CLAUDE.md §9 の「当日のデータだけで把握できる方が望ましい」を確かめるため、平常期を使わない版を同じデータで動かした（`scripts/synth/detect_demo.py --no-baseline`）。

| | 平常期あり（本線） | 当日だけ |
|---|---|---|
| 自宅 | 平常 14 日の 3:00 の位置の中央値 | **地震前の最後の夜（当日 3:00）の位置**。1 晩ぶんだけ |
| いつもの場所・探索型 | 使う | 使わない（自宅の周り 200m だけ除く） |
| 期待値の配分 | 平常期のマス別の滞在の割合 | **国勢調査のメッシュ人口**の割合 |
| 検知 | 31/31 | **31/31** |
| 検知までの時間（中央値 / 最大） | 30 分 / 80 分 | 30 分 / 90 分 |
| 誤報（地震より後に始まった候補） | 1 | **6**（D0 1、D1 1、D2 4） |

当日だけ版の誤報 6 件のうち D2 の 4 件は、出勤が戻った職場（30% が出勤する設定）。平常期を知らないと職場を「いつもの場所」として除けないため。
地震より前に始まった候補（出勤・登校）は両方とも数えていない（平常の生活なので）。当日だけ版はそれが 47 件あり、**地震より前は当日だけ版が使えない**ことも分かる。

**平常期は何日あれば足りるか**（`--learn-days N`。地震の直前 N 日を分析に使う。7/27 が月曜なので 1 日 = 月、2 日 = 日月、3 日 = 土日月、5 日 = 水〜月）

| 平常期の日数 | 0（当日だけ） | 1 | 2 | 3 | 5 | 7 | 14 |
|---|---|---|---|---|---|---|---|
| 検知 | 31/31 | 31/31 | 31/31 | 30/31 | 31/31 | 31/31 | 31/31 |
| 誤報 | 6 | 3 | 4 | 4 | **1** | 1 | 1 |

- 1 日でも誤報が 6 → 3 に減る。差は「いつもの場所」ではなく（1 日では 2 日以上の場所が作れない）、期待値の配分が人口から実際の滞在の分布に変わるため
- 平日が 2 日以上入る **5 日で誤報 1** に落ち着く。職場を除くには平日 2 日あればよい
- 3 日（土日月）で 1 件見逃したのは、休日に行った大型店（ゆめタウン）が「いつもの場所」になり、再開した店の行列を除いてしまったから。休日の買い物先を除外に入れるかどうかは、「開いている店」を見つけたいなら入れない方がよい（課題 §8）

結論:
- **集まりを見つける力は同じ**。平常期が要るのは誤報を減らすためだけ（6 → 1）
- 誤報 6 件は「現地の人に聞いて確定する」仕組みで消せる量（§4 の検証でも 1 日 3 件の確認を前提にしている）
- よって **当日だけ版を基本にし、平常期のデータがある人はそれで職場を除く**、の 2 段構えにできる。アプリを入れた当日から動き、平日 2 日（5 日ぶん）で誤報が 1 日 0〜1 件に落ち着く。位置の保存期間も 1 週間程度でよい（プライバシーの利点）
- 人口で配分する期待値は、国勢調査のメッシュ人口さえあればどの市でも使える（八代市に限らない）

判定の基準は seed 1 で決めた。それを変えずに、乱数の seed だけ変えた 3 本（家・役割・いつもの店・集まりに来る人がすべて引き直される）で測った。

| seed | 平常期あり: 検知 / 誤報 / 検知まで（中央値・最大） | 当日だけ: 検知 / 誤報 / 検知まで |
|---|---|---|
| 1（調整用） | 31/31 / 1 / 30 分・80 分 | 31/31 / 6 / 30 分・90 分 |
| 2 | 31/31 / 0 / 30 分・80 分 | 31/31 / 6 / 30 分・60 分 |
| 3 | 31/31 / 2 / 30 分・100 分 | 31/31 / 6 / 30 分・60 分 |
| 4 | 31/31 / 1 / 30 分・70 分 | 31/31 / 3 / 30 分・60 分 |
| **測定用 3 本の合計** | **93/93、誤報 3（1 日 0.3 件）、中央値 30 分** | **93/93、誤報 15（1 日 1.7 件）、中央値 30 分** |

調整用と同じ結果が出た。検知率は 3 本とも 100%、誤報は平常期ありで 1 日 0〜0.7 件、当日だけで 1 日 1〜2 件。
再現: `python scripts/synth/make_demo_data.py --seed 2 --out <置き場>` → `python scripts/synth/detect_demo.py --out <置き場>`（`--no-baseline` も）。

### 4.3 参加率を変えると、何人の集まりまで見えるか

合成データの 1000 人は市民の縮図（集まりの人数は実際の規模）なので、参加率 p のときは集まりに来る人の p だけがアプリ利用者になる。
人を無作為に間引いて（平常期の分析も間引いた人だけで行う）、seed 1〜4 の 4 本 × 参加率 5 段階で検知率を測った（`scripts/synth/participation.py`。判定の基準は変えていない: 5 人以上、p < 1/1000）。
表の分母は 4 本ぶんの集まりの件数（公式を除く 31 件 × 4）。

| 集まりの人数 | 参加率 5% | 参加率 10% | 参加率 20% | 参加率 50% | 参加率 100% |
|---|---|---|---|---|---|
| 〜29 人 | 0/80 | 0/80 | 6/80 | 60/80 | 80/80 |
| 30〜59 人 | 0/28 | 1/28 | 9/28 | 27/28 | 28/28 |
| 60 人〜 | 2/16 | 7/16 | 15/16 | 16/16 | 16/16 |
| 誤報（1 本あたり、3 日） | 0.0 | 0.0 | 0.0 | 0.2 | 1.0 |

読み方:
- 候補になるには「いつもと違う滞在」が **5 人以上**要るので、目安は **集まりの人数 × 参加率 ≥ 5**。参加率 5% なら 100 人以上、10% なら 50 人以上、20% なら 25 人以上の集まりから見え始める（表の 60 人〜の列がそのとおりに動いている: 5% で 2/16、10% で 7/16、20% で 15/16）
- 個人店の炊き出し（25〜35 人）や団地の給水車（20〜50 人）を見つけるには、参加率 20% で一部、50% でほぼ全部。**参加率 5〜10% では見えない**
- 間引くと誤報も減る（5〜20% で 0 件）。人が少ないと、偶然 5 人が同じマスに集まることがないため
- これは CLAUDE.md §3 の見立て（参加率 5% なら 200 人規模から）と合う。実データでの数字（CLAUDE.md §4）とは別に扱う

発表での言い方: 「アプリを入れた人の割合が 5% なら 100 人規模、20% なら 25 人規模の集まりが見える。小さな炊き出しまで拾うには、防災アプリへの組み込みなどで参加率を上げる必要がある」。

### 4.4 回答の型で作ったデータ（`--templates`）

友人の記入フォーム（回答は公開しない。フォームは 2026-11-08 に閉じた）の回答 15 件（2026-11-06 時点。型になるのは 12 人）から行動の型を取り出し、PARAMS の確率の代わりに型から 1 日の予定を作った（docs/demo-data-design.md §3「回答の型から作る」）。集まりの規模・場所・時間帯は同じ台本で、変わるのは背景の動き（通勤・買い物・知人の家）と、集まりでの滞在の長さ（回答の 15〜120 分。集まりより長ければ集まりの長さに収める）。

| | PARAMS 版（§4.2） | 回答の型版 |
|---|---|---|
| 検知（4 seed 合計） | 124/124 | 124/124 |
| 検知までの時間（中央値） | 30 分 | 30 分 |
| 誤報（4 seed 合計、3 日） | 3 | 42（うち店 37） |

- 見逃しなし。11-05 の回答（11 人）で作ったときは 2 件見逃した（seed 2・4 の八代城跡公園の車中泊、3〜4 人。5 人未満なので基準どおり）。集まりに選ばれる人が無作為なので、型が変わると人数も変わる
- 誤報 42 件のうち 37 件は**災害後の買い物**（回答の 12 人中 4 人が、地震の翌日以降に店へ行っている: 水や食料の買い出し、営業している店）。PARAMS 版は「翌日は店が閉まる」と仮定していたので、この誤報は出なかった。本人がふだん行かない店（または平常期に見ていない店）に 5 人以上が同じ時間帯に来ると候補になる
- これは §8 の課題 4（店を「いつもの場所」からどう扱うか）そのもの。確認の質問で「店が開いている」と答えてもらえれば、原体験の「やっている店とやっていない店の差」を埋める情報になる。候補を消すのではなく、種類「店（営業中）」を足す案を検討する。残り 5 件は、公園・団地・職場の近くに 5〜6 人が同じ時間帯に重なったもの
- 回答が 12 人分なので、1 つの型が 80 人ほどに複製される。1 人の「2km 先の店へ 14 時に 1 時間」が 80 人の同時行動になり、店の多いマスに集まる。時刻を ±60 分ずらしても消えない。**型の数が増えるほど薄まる**ので、回答が 30〜50 件になったら作り直す
- 数字は合成データ（縮図）での値。実データの数字（CLAUDE.md §4）とは別に扱う

```sh
python scripts/synth/survey_templates.py data/survey-answers-2026-11-06.json --out data/out/survey_templates.json
for s in 1 2 3 4; do
  python scripts/synth/make_demo_data.py --seed $s --templates data/out/survey_templates.json --out data/out/survey/s$s
  python scripts/synth/detect_demo.py --out data/out/survey/s$s
done
```

## 5. 採らなかった方式（CLAUDE.md §3）

| 方式 | 採らない理由 |
|---|---|
| 場所ごとの人数を平常時と比べる（既存研究の主流。瀬戸ほか 2016、Yabe ほか 2016） | 中心部では背景の人に埋もれる。災害日は街全体が変わって崩れる。避難所になる学校は休校で「いつもより少ない」になる |
| 移動の向き（1 点に向かってくる人） | 道路を移動する人の進む先が多くの場所と重なり、誤報が多すぎる |
| 機械学習（LLM・深層学習） | コストと説明のしやすさ。ポアソンの 1 行で説明でき、AI なしで成立する |

## 6. 先行研究との関係（詳しくは CLAUDE.md §6、README）

- 個人の移動の規則性と逸脱（Song ほか 2010）→ ②「その人の平常」を基準にする根拠
- 探索型の人の存在（Pappalardo ほか 2015）→ ②③ の重み 0.5
- 個人単位でイベント参加を判定（Traag ほか 2011）→ 最も近い先例。本方式は確率的な位置推定をせず、GPS の滞在を直接使う
- 災害時は平常比較が崩れる（Jiang ほか 2019、Fan ほか 2015）→ ④ 街全体の量で基準を動かす根拠

## 7. 動かし方

```sh
python scripts/synth/make_demo_data.py --out data/out   # 合成データ（約 3 分、numpy が要る）
python scripts/synth/detect_demo.py --out data/out      # 検知と答え合わせ（約 40 秒）→ data/out/detect_result.md
python scripts/synth/detect_demo.py --no-baseline       # 平常期を使わない「当日だけ」版 → detect_result_nobase.md
python scripts/synth/detect_demo.py --sample 0.1        # 参加率 10% の見立て（人を間引く）→ detect_result_s10.md
python scripts/synth/participation.py --out data/out <seed2 の置き場> ...   # 参加率 × 集まりの人数の表（§4.3）
pytest tests/test_detect.py                       # 純関数のテスト
```

`app/detect.py` の関数はデータの置き場所を知らない（`Stay` の列と平常期の集計を渡すだけ）。DB（`location_points`）から読んで `candidates` に書く定期処理は `app/detect_job.py`（API の中で 5 分ごと。`docs/architecture.md` §6）。

API で通して動かす（検知 → 地図 → 質問 → 確認）:

```sh
docker compose up -d --build --wait
python scripts/synth/simulate.py --people 300 --days 8        # 合成データを API 経由で投入（地震の翌日 = 今日にずらす。数分）
docker compose exec api python -m app.detect_job        # 今の時刻で検知（5 分ごとにも自動で回る）
curl -s "$BASE/v1/spots"   # $BASE は起動したサーバーの URL
curl -s "$BASE/v1/spots" -H "Authorization: Bearer <token>" | jq '.features[] | select(.properties.source=="detected")'
```

画面では検知の候補が `?` のピンで出て、近くにいる人に「近くで人が集まっています」と聞く。1 人が種類を答えると確認済みになる。
定期処理が分析する平常期は 7 日、調べる幅は 3 時間で、平常の滞在がまだ 1 件もないときは期待値の下限（0.3）だけになり、5 人以上の「いつもと違う滞在」の集まりはそのまま候補になる（確認で消す前提）。

## 8. これからの課題

1. 平常期が短い人（アプリを入れたばかり）は「当日だけ」版（§4.1）で扱う。平常期が溜まった人から「いつもの場所」の除外に切り替える
2. 集まりが 2 つのマスにまたがるとき、半分ずつに割れて見逃すことがある（マスをずらした集計を重ねる、または滞在の位置でクラスタリングする）
3. 定期処理の分析（自宅・いつもの場所・マスの割合）は 24 時間に 1 回にして、あいだは覚えたものを使う（`app/detect_job.py` の `learn_cached`）。新しく参加した人は次の分析まで「当日だけ」版で扱う。プロセスを再起動すると分析し直す
4. 「いつもの場所」から店を外すかどうか。休日の大型店がいつもの場所になると、再開した店の行列（開いている店の情報）を見逃す。職場（平日の昼に長くいる場所）だけを除く案を試す
